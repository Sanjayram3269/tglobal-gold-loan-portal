## 1. Product overview

The portal offers two equivalent ways to start a preliminary gold-loan application:

1. **Guided application:** The borrower enters their details, reviews a live quote, selects a plan, reviews the full application summary, and explicitly confirms submission.
2. **AI-assisted application:** The borrower explains their gold-loan requirements conversationally. The assistant gathers missing information, calls typed backend tools, displays a quote generated by the same backend service, and requests explicit confirmation before submission.

Both paths use the **same validated API and business service**. The language model is not a source of truth for eligibility, interest rates, plan details, or financial arithmetic.

An admin view lists submitted applications newest first. Mobile numbers are masked in responses and in the interface.

### Important product boundary

This is a preliminary eligibility demonstration, not a loan approval engine. The seeded 24K gold rate is a mock value of **₹7,000 per gram**. No real lending decision, identity verification, market-price feed, or financial advice is provided.

## 2. Goals and engineering principles

The assignment will be built around these principles:

- **Correctness before breadth:** Complete and verify all required functionality before adding optional features.
- **One source of truth:** The backend recalculates every quote and application amount.
- **Exact money handling:** Avoid binary floating-point arithmetic for money; use integer paise and/or exact decimal arithmetic with explicit rounding.
- **Validate at boundaries:** Validate API bodies and AI tool arguments with shared Zod schemas.
- **Safe side effects:** Never submit an application merely because the model suggests doing so. Require an explicit confirmation action in the UI and enforce the rule in backend orchestration.
- **Consistent errors:** Return structured, predictable errors with appropriate HTTP status codes.
- **Privacy by default:** Never return full mobile numbers in lead-list responses or write them to application logs.
- **Test critical behavior:** Unit-test financial rules, integration-test HTTP behavior, and evaluate the required AI conversations.
- **Reproducible setup:** Include migrations, deterministic seed data, environment examples, automated tests, and clear instructions.
- **Honest AI-assisted development:** Record tools used, prompts, mistakes found, and regression tests in `AI_LOG.md`.

## 5. Architecture

```text
React borrower form ─────┐
                         │
React AI chat ────────────┼──> Express API ──> Zod validation
                         │                       │
Admin dashboard ─────────┘                       v
                                           Loan service
                                      (single source of truth)
                                                 │
                                                 v
                                             PostgreSQL

AI orchestrator ──> get_loan_schemes ────────────┘
                ├─> calculate_quote ──> quote API / loan service
                └─> submit_application ──> lead API / loan service
```

### Architectural rules

1. Routes handle HTTP concerns, not financial formulas.
2. Zod schemas validate all external input.
3. A shared loan service owns calculations and application creation rules.
4. Both the UI and the AI agent call the same backend contracts.
5. The LLM may interpret language and choose a tool, but it does not own financial facts or calculations.
6. Application submission and duplicate protection are enforced by the server and database—not by prompt instructions alone.
7. Provider credentials stay on the server.

## 6. Borrower and admin workflows

### Borrower form: three steps

**Step 1 — Details**

Collect:
- Name
- Indian mobile number
- Gross jewellery weight in grams
- Net gold weight in grams
- Karat: 18K, 22K, or 24K

Show inline validation and useful input modes. Net weight must not exceed gross weight.

**Step 2 — Live quote**

- Debounce quote requests by approximately 300 ms.
- Call `POST /api/v1/quotes`.
- Show pure gold grams, gold value, and eligible loan for each plan.
- Let the borrower select a plan.
- Clearly label the offer as preliminary and based on the mock rate.

**Step 3 — Review and submit**

- Show all submitted details, selected plan, and server quote.
- Require a deliberate confirmation action.
- Call `POST /api/v1/leads`.
- Display the application ID on success.
- Translate a duplicate `409` into a friendly message that includes the existing application ID.
- Preserve entered values when an error can be corrected safely.

### AI-assisted flow

The assistant asks for missing information, uses backend tools to fetch plans and quotes, and presents a review summary. A separate UI confirmation action authorizes submission. If the borrower changes their mind, the assistant must not submit.

### Admin view

- Newest applications first.
- Masked mobile number, e.g. `9876XXXX10`.
- Net weight, plan, eligible loan, status, and submission time.
- Filter by plan.
- Friendly empty, loading, and error states.

**Security note:** A lead-list endpoint is not equivalent to admin authentication. If this were deployed beyond a local demonstration, the admin view and its API would need authentication and authorization. The demo must not be represented as production-secure for real borrower data.

## 7. Financial calculation rules

### Seeded configuration

Mock 24K gold rate: **₹7,000 per gram**

| Plan ID | Plan | Annual interest | Maximum LTV | Tenure |
|---|---|---:|---:|---|
| `PLAN_BULLET_01` | Bullet Repayment | 12.0% | 70% | 12 months; principal and interest at maturity |
| `PLAN_EMI_01` | Monthly EMI | 10.5% | 75% | 12 months; equal monthly instalments |

The eligible-loan calculation uses the lower of the plan LTV and 75%.

### Formulas

```text
pureGoldGrams = netWeightGrams × (karat / 24)

goldValue = pureGoldGrams × rate24kPerGram

effectiveLtv = min(plan.maxLtv, 0.75)

eligibleLoanRupees = floor(goldValue × effectiveLtv)
```

The amount shown as the eligible loan is a whole number of rupees, rounded down. Intermediate calculations must preserve sufficient precision to avoid floating-point boundary errors. Monetary values persisted in the database should use integer paise or an exact decimal representation—not floating-point columns.

### Required reference cases

| Input | Expected result |
|---|---|
| Net 45 g, 22K, Monthly EMI | Pure gold `41.25 g`; value `₹288,750`; loan `₹216,562` |
| Net 45 g, 22K, Bullet | Value `₹288,750`; loan `₹202,125` |
| Net 10 g, 18K, Monthly EMI | Pure gold `7.5 g`; value `₹52,500`; loan `₹39,375` |
| Net 52 g, gross 50 g | `400` with a field error on `netWeightGrams` |
| Mobile `5876543210` or `98765` | `400` with a field error on `mobileNumber` |
| Same mobile submitted again within seven days | `409` with the existing `applicationId` |
| Same request and same idempotency key (bonus) | Replay the original successful response |
| Two simultaneous requests for the same new mobile (bonus) | Exactly one `201` and one `409` |

### Input constraints

- Name: 2–60 characters; letters and spaces only, as specified in the assignment.
- Mobile: `^[6-9]\d{9}$`.
- Weight: `0 < netWeightGrams <= grossWeightGrams <= 1000`.
- Karat: `18`, `22`, or `24`.
- Plan ID must refer to an existing plan.
- Server recalculates the quote at submission time.

**Interest-rate clarification:** The assignment specifies the interest rates and repayment styles, but its eligible-loan reference table does not ask for an EMI or maturity repayment amount. The initial quote will implement the specified eligibility calculation and expose plan terms. Any displayed repayment estimate must be explicitly labelled and separately tested; it must not alter the eligible-loan calculation.

## 8. API contract

Base path: `/api/v1`

### `GET /api/v1/loan-schemes`

Returns active plans from the database, including ID, name, annual interest rate, tenure, and maximum LTV. Seeded plans must not exceed 75% LTV.

### `POST /api/v1/quotes`

Validates weights and karat, reads active plans, and returns pure gold, gold value, and eligible loan per plan. This endpoint is read-only.

Illustrative request:

```json
{
  "netWeightGrams": 45,
  "grossWeightGrams": 50,
  "karat": 22
}
```

### `POST /api/v1/leads`

Validates the borrower details and plan, recalculates the quote server-side, checks duplicates, persists the lead as `SUBMITTED`, and returns `201` with an `applicationId`.

The client must not be allowed to determine the persisted loan amount by sending a trusted quote. The server should derive it from validated input and the current plan configuration.

### `GET /api/v1/leads`

Returns leads newest first. Mobile numbers must be masked in every response. Plan filtering is required in the UI; server-side pagination is a useful additional improvement.

### Consistent error format

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Please correct the highlighted fields.",
    "fields": [
      {
        "field": "netWeightGrams",
        "message": "Net weight cannot exceed gross weight."
      }
    ]
  }
}
```

All error responses should follow one documented shape. Expected statuses include `400`, `404`, `409`, and a sanitized JSON `500`. Internal stack traces and sensitive values must never be returned to clients.

## 10. AI Loan Assist design

### Required tools

#### `get_loan_schemes()`

Reads active schemes from the backend. The assistant may only describe plan details returned by this tool.

#### `calculate_quote(net, gross, karat)`

Validates arguments and calls the same quote service used by the borrower form. The LLM must not calculate or invent financial values.

#### `submit_application(payload)`

Validates the application payload and uses the normal lead-creation service. The tool is not allowed to bypass the confirmation gate.

### Confirmation enforcement

The LLM's text saying “the user confirmed” is not sufficient authorization. The UI must capture an explicit confirmation action tied to the exact application summary. The backend orchestration must verify that confirmation state before executing the side effect. If the details change after review, the old confirmation becomes invalid and the summary must be reviewed again.

### Guardrails

- Stay within gold-loan intake and scheme questions.
- Do not provide investment advice or guarantee approval.
- Ask for missing details instead of guessing.
- Validate tool arguments with the same schemas as the API.
- Return tool errors to the assistant so it can ask the user to correct inputs.
- Do not expose API keys or full mobile numbers in logs.
- Treat prompt-injection attempts as untrusted user input.
- Support cancellation and corrections without accidental submission.
- Handle provider timeouts, malformed tool arguments, and tool failures without inventing results.

### Provider independence

A small adapter will isolate provider-specific request and tool-calling formats. Core financial tests, API tests, and most agent orchestration tests will use deterministic mocks. The chosen provider, model, setup instructions, and any limitations will be documented here once decided.

## 11. Validation, errors, and security

- Validate all external request bodies with Zod.
- Revalidate AI tool arguments on the server.
- Normalize mobile numbers before duplicate checks.
- Mask mobile numbers in list responses and redact them from logs.
- Never trust client-supplied quote amounts or plan terms.
- Enforce the 75% maximum LTV on the server.
- Use environment variables for credentials and database URLs.
- Commit `.env.example`, never real `.env` files or API keys.
- Use Helmet, explicit CORS configuration, and sanitized error handling.
- Avoid logging complete request bodies for borrower endpoints.
- Apply database transactions and an appropriate concurrency strategy to lead creation.
- Add rate limiting for lead creation and AI chat before any public deployment.
- Clearly distinguish demo-only behavior from production security controls.

A real production lending product would additionally require authenticated borrower/admin access, authorization, secure handling and retention of personal data, audit controls, monitoring, and review of applicable legal and regulatory requirements. Those are not claimed as completed by this assignment.

## 12. Testing and evaluation

### Financial unit tests

- All three required reference calculations.
- Whole-rupee flooring at rounding boundaries.
- 18K, 22K, and 24K.
- Zero, negative, over-limit, and invalid weights.
- Net weight greater than gross weight.
- LTV cap never exceeds 75%, including a misconfigured plan.
- Quote calculation has no database side effects.

### API integration tests

- Active schemes returned from seeded database.
- Valid quote request.
- Invalid body returns `400` and field errors.
- Unknown scheme returns `404`.
- Successful lead creation returns `201`.
- Same mobile within seven days returns `409` and the existing application ID.
- Lead-list response masks mobile numbers and sorts newest first.
- Internal errors return sanitized JSON.
- Concurrent duplicate submissions result in one successful creation and one conflict.

### Five required conversation evaluations

1. **Happy path:** Gather information, quote through tools, review, confirm, and submit.
2. **Missing field:** Ask for the missing field before quoting or submitting as appropriate.
3. **Duplicate:** Surface the `409` response and existing application ID.
4. **Off-topic request:** Politely decline and do not trigger unrelated actions.
5. **Invalid weights:** Reject net weight greater than gross weight and do not submit.

### Additional AI evaluations

- Prompt-injection attempt to ignore rules or invent a quote.
- Hinglish request.
- Borrower changes their mind before confirmation.
- Invalid or malformed tool arguments.
- LLM/provider timeout.
- Tool failure or unexpected response.
- Attempted submission without a UI confirmation.
- Details changed after confirmation.
- Model-generated amount conflicts with backend quote.
- At least ten automated scenarios if time allows.

LLM-dependent evaluations should use fixed model settings where possible, record expected outcomes, and avoid making the core test suite dependent on unpredictable model output.

## 14. Local development

### Prerequisites

- Node.js 22 and npm.
- PostgreSQL 17 (Docker or a local installation).
- A Groq API key for live AI assistant conversations. Unit/API tests and production builds should not require a live LLM key.

### Setup

```powershell
git clone https://github.com/Sanjayram3269/tglobal-gold-loan-portal.git
cd tglobal-gold-loan-portal
npm ci
Copy-Item .env.example apps/api/.env
```

Edit `apps/api/.env` and set `DATABASE_URL` to your PostgreSQL connection string and `GROQ_API_KEY` to your own server-side key. Do not commit this file.

Apply migrations and seed the loan schemes:

```powershell
npm exec --workspace=@tglobal/api prisma -- migrate deploy
npm run seed --workspace=@tglobal/api
```

Start the API and Vite frontend:

```powershell
npm run dev
```

Vite uses port 5173 when available and may select 5174 or another port if that port is occupied. The API defaults to port 4000. Open the exact URL printed by Vite.

Run tests and production builds:

```powershell
npm run test --workspace=@tglobal/api
npm run build
```

The root `npm test` script is also available. GitHub Actions runs the API test suite and production build on pushes and pull requests.

## 15. Environment variables

The root `.env.example` is a safe template. Copy it to `apps/api/.env` for local development and supply your own values.

- `DATABASE_URL`: PostgreSQL connection string.
- `PORT`: API port (defaults to 4000).
- `WEB_ORIGIN`: comma-separated allowed browser origins for local Vite development.
- `GROQ_API_KEY`: server-side key required for live AI conversations.
- `GROQ_MODEL`: Groq model identifier (defaults to `openai/gpt-oss-20b`).
- `VITE_API_URL`: optional frontend API URL override; Vite-exposed variables are public, so never put secrets in them.

Never commit real credentials. If a real key has ever been committed or exposed, revoke or rotate it.
